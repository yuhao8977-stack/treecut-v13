# P2.5 并行分析引擎 — 架构设计

- **版本**：v1.0（设计稿）
- **对应审计**：docs/P2.5_UPGRADE_AUDIT.md
- **目标**：单 Worker 串行 → 多 Worker 并行任务调度系统，旁路兼容运行中 P2 任务
- **日期**：2026-08-22

---

## 1. 总体架构

```
CLI: treecut.main --p2.5-run [--workers 3] [--limit N] [--stages scene,keyframe,asr,ocr]
        │
        ▼
TaskScheduler (analysis/scheduler.py)
  │  生成任务 → analysis_tasks 表（仅未来新增，不碰旧任务）
  │
  ├──► WorkerPool (analysis/worker_pool.py)
  │       │  multiprocessing spawn × N
  │       ├──► Worker: 视觉 (scene+keyframe)   ← 按 stages 分片
  │       ├──► Worker: ASR (whisper)
  │       └──► Worker: OCR (rapidocr)
  │              │
  │              ▼
  │       TaskStore.claim_task()   ← BEGIN IMMEDIATE 原子领取（防重复）
  │              ▼
  │       执行分析（复用现有引擎类）
  │              ▼
  │       TaskStore.complete_task() / fail_task()
  │              ▼
  │       asset_processing_state 同步更新（旁路：兼容旧 UI/统计）
  ▼
worker_p25.log  （每 Worker 独立日志）
```

**关键决策**：
1. **旁路**：新增 `analysis/scheduler.py`、`analysis/worker_pool.py`、`analysis/worker_p25.py`、`library/task_store.py` 四个模块；`p2_worker.py`、`main.py` 旧参数**保持原样**。运行中 PID 19152 不受影响。
2. **新任务表**：`analysis_tasks` 是调度层的唯一事实来源；`asset_processing_state` 仅作为**幂等护栏**（写入结果前检查，DONE/SKIPPED 则跳过）。
3. **分片方式**：默认 3 Worker 按**阶段职责**分片（视觉/ASR/OCR），每个 Worker 领取"自己负责阶段"的任务；也支持同阶段多 Worker（--workers 覆盖）并行领取不同 asset。
4. **与旧任务的边界**：`analysis_tasks` 只登记"P2.5 调度器创建的任务"。旧 `--p2-run` 继续用 `asset_processing_state` 自行推进；两者通过阶段状态互斥（见 §5）。

## 2. 模块设计

### 2.1 `library/task_store.py` — TaskStore（任务存储 + 原子领取）

```python
class TaskStore:
    SCHEMA_VERSION = 1

    def ensure_schema(self) -> None            # CREATE TABLE IF NOT EXISTS analysis_tasks + schema_version
    def create_tasks(self, asset_ids: list[str], task_type: str, priority: int = 0,
                     stages: list[str] | None = None) -> int   # 幂等：已存在(asset_id,task_type)跳过
    def claim_task(self, worker_id: str, task_type: str, stages: list[str] | None = None) -> dict | None
        # BEGIN IMMEDIATE
        #   SELECT ... WHERE status='pending' AND retry_count<=MAX_RETRY
        #   ORDER BY priority DESC, created_at ASC LIMIT 1
        #   UPDATE SET status='processing', worker_id=?, started_time=?, attempt=attempt+1
        # COMMIT
    def complete_task(self, task_id, result: dict | None = None) -> None
    def fail_task(self, task_id, error: str, retryable: bool = True) -> None
        # retryable → status='pending', retry_count+1；超上限 → 'failed'
    def pending_count(self) -> int
    def stats(self) -> dict
    def recover_stale(self, max_age_seconds: float = 1800) -> int   # processing 超时回收为 pending
```

**原子领取 SQL（核心）**：
```sql
BEGIN IMMEDIATE;
SELECT t.task_id, t.asset_id, t.stages, a.media_id, m.relative_path, s.path AS source_path,
       m.available, s.online
FROM analysis_tasks t
JOIN assets a ON a.asset_id = t.asset_id
JOIN media_files m ON m.id = a.media_id
JOIN sources s ON s.id = m.source_id
WHERE t.status = 'pending' AND t.retry_count <= :max_retry
  AND m.available = 1 AND s.online = 1
  AND (:task_type = '' OR t.task_type = :task_type)
ORDER BY t.priority DESC, t.created_at ASC
LIMIT 1;
-- 命中则 UPDATE status='processing' ... ; 检查 rowcount==1 才返回
COMMIT;
```
多进程并发下，SQLite 的 `BEGIN IMMEDIATE` 串行化写事务，第二个 Worker 会拿到 `SQLITE_BUSY` 后重试（busy_timeout=30s），不可能双领。

### 2.2 `analysis/scheduler.py` — TaskScheduler

```python
class TaskScheduler:
    def __init__(self, paths: RuntimePaths | None = None): ...
    def sync_from_state(self, stages: list[str]) -> dict
        # 扫描 asset_processing_state 中 stage ∈ stages 且 status NOT IN (DONE, SKIPPED)
        # 的 asset → 写入 analysis_tasks（幂等 upsert），返回 {created, skipped_done, total}
    def run(self, workers: int = 3, limit: int | None = None,
            stages: list[str] | None = None) -> SchedulerResult
        # 1) sync_from_state() 生成任务
        # 2) WorkerPool(workers).run(limit)
        # 3) 循环直到 pending==0 或达到 limit
```

**任务来源**：`sync_from_state` 是**唯一**任务入口，只登记"当前未完成"的 asset+stage，天然满足"已完成的跳过、处理中的等待、失败的 retry"（第七阶段要求）。

### 2.3 `analysis/worker_p25.py` — P2.5 阶段 Worker（进程内执行）

```python
class Worker25:
    def __init__(self, worker_id: str, stages: list[str], paths: RuntimePaths,
                 asr_model: str = "small"): ...
    def run(self, limit: int | None = None) -> dict
        # 循环:
        #   task = store.claim_task(worker_id, ...)
        #   if not task: break
        #   幂等护栏: ps.should_process(...) == SKIP_ALREADY_DONE → complete(skip)
        #   按 stage 分派: scene/keyframe/asr/ocr（复用 SceneDetector/KeyframeExtractor/
        #                 WhisperEngine/OcrEngine）
        #   store.complete_task / fail_task（含重试上限）
        #   写 worker_p25.log（worker_id/asset_id/stage/耗时/结果）
```

**阶段分片（默认）**：
- Worker 视觉：`stages=["scene","keyframe"]` → `task_type="vision"`
- Worker ASR：`stages=["asr"]` → `task_type="asr"`
- Worker OCR：`stages=["ocr"]` → `task_type="ocr"`

每个 Worker 进程只加载自己需要的模型（视觉 Worker 不加载 whisper，OCR Worker 不加载 cv2 大模型），**内存隔离**，模型常驻。

### 2.4 `analysis/worker_pool.py` — WorkerPool（多进程）

```python
def _pool_entry(worker_id, stages, db_path, log_path, limit, stop_event):

class WorkerPool:
    def __init__(self, workers: int, stages: list[str], paths: RuntimePaths): ...
```

## 3. 任务生命周期

```
pending ──claim_task──► processing ──complete_task──► completed
   ▲                        │
   │   fail_task(retryable) │ (超时 recover_stale)
   └────────────────────────┘
   │ retry_count > MAX_RETRY(3)
   ▼
 failed
```

| 状态 | 含义 |
|---|---|
| `pending` | 可被领取 |
| `processing` | 已被某 Worker 领取，记录 worker_id/started_time |
| `completed` | 成功（含 SKIP_ALREADY_DONE） |
| `failed` | 超过重试上限 |
| `skipped` | 前置条件不满足（如无 segments） |

## 4. 数据库设计（详见 DATABASE_MIGRATION.md）

**新增表 `analysis_tasks`**：
```sql
CREATE TABLE IF NOT EXISTS analysis_tasks (
    task_id       TEXT PRIMARY KEY,           -- 'p25_' + uuid4().hex
    asset_id      TEXT NOT NULL REFERENCES assets(asset_id) ON DELETE CASCADE,
    task_type     TEXT NOT NULL,              -- vision|asr|ocr|full
    stages        TEXT NOT NULL DEFAULT '',   -- 'scene,keyframe' 等
    status        TEXT NOT NULL DEFAULT 'pending',  -- pending/processing/completed/failed/skipped
    worker_id     TEXT NOT NULL DEFAULT '',
    priority      INTEGER NOT NULL DEFAULT 0,
    retry_count   INTEGER NOT NULL DEFAULT 0,
    attempt       INTEGER NOT NULL DEFAULT 0,
    error         TEXT NOT NULL DEFAULT '',
    created_time  REAL NOT NULL,
    started_time  REAL,
    finished_time REAL,
    UNIQUE(asset_id, task_type)
);
CREATE INDEX IF NOT EXISTS idx_analysis_tasks_status
    ON analysis_tasks(status, priority DESC, created_at);
```

**新增版本表 `schema_version`**（废除 user_version 依赖）：
```sql
CREATE TABLE IF NOT EXISTS schema_version (
    name    TEXT PRIMARY KEY,     -- 'analysis_tasks'
    version INTEGER NOT NULL
);
```

## 5. 与运行中 P2 任务的互斥（第五阶段核心）

| 场景 | 处理 |
|---|---|
| P2.5 启动时旧 PID 19152 仍在跑 | **默认策略：不并行抢跑**。`scheduler.run()` 检查 `asset_processing_state` 中 PROCESSING 数量，若 >0 且为旧进程持有，则等待/提示；用户可用 `--force` 强制并行（此时互斥靠状态机：新 Worker claim 前检查 stage 非 PROCESSING） |
| 同一 asset 旧任务正在处理 | 新 Worker `claim_task` 后，写入前再查 `ps.should_process()`：若状态 PROCESSING（旧进程持有）→ `fail_task(retryable=False)` 标记 skip 并跳过，避免双跑 |
| 旧任务已完成（DONE） | `sync_from_state` 不生成任务（`status NOT IN (DONE,SKIPPED)` 过滤）→ 天然跳过 |

**互斥不变量**：一个 (asset_id, stage) 在同一时刻**最多一个**执行者——P2.5 用 `analysis_tasks` 原子领取 + `asset_processing_state` 状态断言双重保证。

## 6. 资源调度（第六/九阶段）

| 资源 | 现状 | P2.5 默认 | 可调 |
|---|---|---|---|
| CPU | 12 核，P2 用 ~4.4 核 | 3 Worker × ~2-3 核 ≈ 6-9 核 | `--workers N` |
| 内存 | 32 GB | 3 模型常驻 ≈ 3-5 GB | `--workers` |
| GPU | RTX 3050 6GB（闲置） | 默认 CPU | `--device cuda`（预留，需装 CUDA 运行时） |

**限流**：每 Worker 每轮只 claim 1 个任务（单任务粒度），完成后立即 claim 下一个 → 天然自适应负载，无批分配浪费。

## 7. 日志（第八阶段）

- 文件：`<data_root>/logs/worker_p25.log`（共享）+ `worker_{id}.log`（每 Worker）
- 字段：`[时间] worker_id | task_id | asset_id | stage | 结果 | 耗时(秒)`
- 样例：`[2026-08-22 16:00:01] worker_001 | p25_ab12 | 000599b6 | scene | success | 3.2`

## 8. 未来扩展预留（第十一阶段）

- **Segment 系统**：`task_type='segment'` 直接进入同一调度（表结构已含 stages 自由组合）
- **Embedding**：`task_type='embedding'`（P4 已有 embed_worker，接入 WorkerPool 即可）
- **AI 视觉理解**：`task_type='vision'` 已预留，Worker 视觉扩展 model 参数
- **模板系统/反馈学习**：任务表无关，不影响调度；`priority` 字段可供未来"高优先任务"插队
- **3TB 素材**：任务按 asset 粒度无限排队，断点恢复靠 `recover_stale` + 任务持久化

---

## 9. 验收标准

1. `--p2.5-status` 显示任务数/状态分布
2. 3 个 Worker 并发处理不同 asset，`asset_processing_state` 无重复 PROCESSING
3. 并发测试（2 进程同时 claim）无双领（见 PERFORMANCE_REPORT.md）
4. 运行中 PID 19152 不受影响（升级期间不重启）
5. 已 DONE 素材零重跑
6. 性能：3 Worker ≥ 2× 单 Worker 吞吐（benchmark 实测）
