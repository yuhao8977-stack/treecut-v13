# TreeCut v13 全盘挑毛病审计报告

审计日期：2026-08-03  
审计对象：`G:\TreeCut_v13` 及干净候选版 `G:\TreeCut_v13_release_candidate`  
审计原则：只认代码、数据库、运行环境和真实输出证据，不以“测试通过”代替功能完成。

## 一、审计范围与总体判断

已逐一解析正式源码 43 个 Python 文件（约 3009 行）、16 个测试文件、7 个脚本、模型目录、便携 Python、SQLite 数据库、运行数据和干净候选版。全部源码可通过 Python 语法解析，61 个现有单元测试仍通过。

但结论不是“已经没有问题”。现版本是能运行的工程化原型，正式链路比 v12 清楚很多，但仍有严重的半成品、无效配置、测试盲区、运行环境重复和跨电脑承诺不成立等问题。以下问题按严重程度列出。

## 二、最高优先级问题（P0，必须先解决）

### P0-01：当前便携包永远不能在 NVIDIA 电脑启用 Qwen

- 证据：便携环境中的 Torch 是 `2.3.1+cpu`；模型策略依赖 `torch.cuda.is_available()`。
- 后果：即使复制到有 NVIDIA 显卡的台式机，CUDA 仍返回 false，5.62GB Qwen 权重不会被调用。
- 性质：Qwen 当前属于“模型和代码都在，但这套运行时不可能运行”的无效大模块。
- 解决：建立 CPU 运行时与 NVIDIA CUDA 运行时两套受控环境，或制作独立 GPU 扩展包；按显卡驱动、计算能力和显存选择。GPU 版必须在目标机器做真实推理、显存峰值和回退测试。

### P0-02：旧分析结果会冒充新分析完成

- 证据：主素材库 32 条任务全标记 `success`，其中 26 条有音轨但没有语音分析结果；旧结果和新工作器都写 `schema_version=1`。
- 后果：文件未变化时不会重新排队，升级后的语音、YOLO、风险和新字段可能永远不执行。
- 解决：增加 `pipeline_version`、各模型版本、配置指纹和结果完整性校验；启动/扫描时把不符合当前指纹的结果标记为 stale 并重新分析，不能只看文件修改时间。

### P0-03：分析成功门槛过低

- 证据：视觉、YOLO、语音异常都被捕获并写入 `error`，只要探测和抽帧成功，任务仍可 `complete_job(success)`。
- 后果：视觉和语音全部失败仍可能显示“分析成功”，属于半假成功。
- 解决：按素材能力建立最低成功合同：至少一个核心视觉结果；有音轨时语音必须成功或明确标为可接受的“无有效人声”；降级成功和完整成功分开显示。

### P0-04：“最终成片”仍然使用预览清晰度

- 证据：生产链只调用 `render_video_plan(..., "preview")`，得到 540×960；代码定义的 1080×1920 `final` profile 从未调用。烧字幕只是重新编码 540×960，无法变成真正高清。
- 后果：软件写着导出最终 MP4，实际是预览级画面。
- 解决：MP4 成片直接按 final profile 渲染；剪映专用流程可不渲染最终 MP4；质量检查要求精确 1080×1920，而不是只要求大于 540×960。

### P0-05：长配音会被静默截断

- 证据：TTS 先生成完整音频和字幕，封装时用视频时长 `-t` 截断；没有检查 `narration_seconds > video_duration`。
- 后果：文案尾部可能消失，字幕时间还能超过成片/草稿总时长。
- 解决：制作前预测和实测配音长度；提供自动扩展画面、自动调速、精简文案或阻止生成四种明确策略；任何截断必须判失败。

### P0-06：配置文件大部分是空架子

- 证据：`output_mode`、`model_mode`、`tts_mode`、`material_sources`、`auto_discover_drives`、`include_network_drives`、`max_parallel_jobs`、`keep_intermediate_files` 只保存和校验，正式代码没有读取。
- 后果：用户改配置以为生效，实际上无效。
- 解决：每个配置项必须接入唯一消费点并有行为测试；暂不支持的项从公开配置删除，不能保留装饰性开关。

### P0-07：正式制作默认允许测试素材

- 证据：`CreativeRequest.include_test_materials=True`、API 默认 True、桌面又硬编码传 True。
- 后果：测试视频可能混入正式客户成片；干净版虽然当前没测试库，但设计默认仍错误。
- 解决：正式默认必须 False；仅开发模式可显式打开，并在界面用醒目警告标注。

## 三、高优先级问题（P1）

### P1-01：扫描支持音频和图片，但分析器明确不支持

- 证据：目录扫描会为视频、音频、图片都创建分析任务；工作器遇到非视频直接抛 `NotImplementedError`。
- 后果：包含照片或音乐的素材库会反复重试并最终失败，制造大量红色任务。
- 解决：拆分 video/image/audio 工作器；在实现前只为支持类型建任务，其他类型登记但标记 `unsupported`，不要假装失败。

### P1-02：SenseVoice 分段缓存可能混入旧音频

- 证据：同一 media_id 的 `chunk_*.wav` 目录在重新生成前没有清空。
- 后果：新视频更短或分段数量减少时，旧尾部分段仍会被读取，转写出不存在的内容。
- 解决：每次使用原子临时目录，成功后替换；缓存键包含文件指纹、模型版本和分段参数。

### P1-03：达到扫描上限时会错误地把未访问文件标为丢失

- 证据：`max_files` 只跳出当前文件循环，目录遍历继续；最后用 `existing - seen` 将未扫描到的旧文件设为 unavailable。
- 后果：大素材库可能被部分扫描后错误下线大量有效素材。
- 解决：达到上限立即停止整个遍历，标记 `stopped_early`；不完整扫描绝不能执行 missing 对账。

### P1-04：剪映草稿音频时间线不完整

- 证据：配音短于成片不补静音；背景音乐只放一遍、不循环；字幕可能越过项目总时长；返回值无条件写 `has_voice=True, has_bgm=True`。
- 后果：长视频后半段没有音乐，轨道边界可能异常，返回状态与真实时间线不一致。
- 解决：循环/裁切 BGM，配音尾部补静音或明确结束，裁切所有字幕到总时长，返回值从实际片段读取。

### P1-05：剪映质量检查过于宽松

- 证据：只查三个文件、时长、至少三条轨道、至少一个视频素材；没有验证配音、音乐、字幕片段、源路径存在、片段边界和剪映实际可打开。
- 后果：空音轨、空字幕或越界草稿仍可能通过。
- 解决：逐轨道/逐片段验证，校验所有素材路径与时间范围；维护多个剪映版本的真实打开验收样本。

### P1-06：物体检测结果没有参与任何决策

- 证据：YOLO 结果只写报告，分类、风险、匹配和选材均不读取。
- 后果：YOLO 是“真实运行但功能上旁路”的半无效模块，增加耗时却不改善结果。
- 解决：定义可测用途，例如人物口播识别、产品/场景证据、危险/无关物体过滤；若不能证明提升则默认关闭。

### P1-07：CPU 风险检查只看一个代表帧且只用英文词表

- 证据：CPU 只对中间帧生成描述，风险词只有 screenshot、bank 等英文词；没有 OCR。
- 后果：开头/结尾的隐私、账号、聊天和支付画面可能漏检。
- 解决：风险筛选使用全部抽样帧；增加本地 OCR、中文风险词、画面类型检测；风险检查与普通描述分开，不因 CPU 模式只看一帧。

### P1-08：模型“就绪”检测只看少量文件存在

- 证据：Florence 只查一个权重，Qwen 只查 config 和两个分片；诊断不加载模型做最小推理，也不校验哈希。
- 后果：权重损坏、处理器缺失、模型代码不兼容仍显示就绪。
- 解决：发布时生成 SHA-256 清单；诊断分为文件完整、可加载、最小推理三级，结果不可混为一个 ready。

### P1-09：便携 Python 存在两套重复包

- 证据：约 0.58GB 包同时位于 `runtime\Lib` 与 `runtime\Lib\site-packages`；同一 distribution 被元数据发现两次。
- 后果：Python 优先加载 Lib 根目录版本；只升级另一份会造成隐蔽版本错乱，也浪费空间。
- 解决：从全新锁定环境构建运行时，只保留标准 `Lib` 与单一 `site-packages` 布局；禁止手工拼接两个环境。

### P1-10：候选版携带大量开发/未启用依赖

- 证据：包含 pip、twine、keyring、edge-tts、FAISS、Matplotlib、Faster-Whisper/ctranslate2 等；Whisper 权重为空，CLIP/BGE 未启用。
- 后果：体积、攻击面和依赖冲突增加；当前 Qwen 权重在 CPU runtime 中又无法使用。
- 解决：建立 `requirements.lock` 和依赖闭包；CPU核心版、GPU扩展、Whisper扩展分包；逐包删除后运行完整回归和真实推理，不能凭名称粗删。

### P1-11：发布脚本和验证脚本硬编码 G 盘

- 证据：发布默认目标固定 `G:\TreeCut_v13_release_candidate`，完整分析脚本固定测试素材路径；部分测试也固定 G 盘。
- 后果：换盘符/换电脑后开发工具失败，与便携目标矛盾。
- 解决：所有路径相对安装根或由参数传入；测试使用运行时临时目录，不依赖某个盘符存在。

### P1-12：桌面启动器可能偷偷使用相邻旧环境

- 证据：找不到自身 `runtime\pythonw.exe` 时，会搜索父目录下其他文件夹的 `runtime_data\venv`。
- 后果：安装损坏时不报错，反而用未知旧 Python 启动，产生“这台能跑、另一台不能跑”的幽灵问题。
- 解决：只允许自身签名/清单内的运行时；缺失就明确失败，不跨目录兜底。

### P1-13：直接模块启动仍可能使用 C 盘 TEMP

- 证据：`apply_environment()` 使用 `os.environ.setdefault`，系统已有 TEMP/TMP 时不会覆盖；启动脚本虽覆盖，但直接运行模块不会。
- 后果：不能严格保证任何入口都不写 C 盘。
- 解决：受控缓存变量强制设置到 data_root；外部覆盖只允许经过显式校验且必须在非 C 盘。

### P1-14：匹配算法容易误命中且没有真正语义匹配

- 证据：中文拆成 2/3/4 字符片段，只要一个片段出现就入选；通用词“设计、空间、实用”会造成弱相关命中。
- 后果：卖点相关性和审美错选率难以稳定。
- 解决：停用词、短语权重、字段置信度、最低覆盖率、同义词和业务词典；之后用真实标注集比较 BGE/CLIP 是否明显优于规则。

### P1-15：重复视频可同时进入同一成片

- 证据：数据库检测 fingerprint 重复，但匹配/规划只按 media_id 去重，不按 fingerprint 去重。
- 后果：同一内容的不同副本可能重复占镜头。
- 解决：候选对象携带 fingerprint；默认按内容指纹去重，并允许用户明确解除。

### P1-16：测试数量高，但关键生产代码覆盖低

- 证据：61 测试通过，但行执行审计显示：ProductionService 约 6.9%、桌面 0%、诊断 0%、MP4 8.9%、Qwen 14.3%、质量中心约 21.9%。
- 后果：多数测试验证小函数和结构，不足以保护完整生产链。
- 解决：增加可重复的端到端夹具，覆盖三种输出、长配音、无音轨、损坏视频、缓存重跑、质量失败、数据库升级、CPU/GPU两环境。

## 四、中优先级问题（P2）

1. `load_candidates` 的 SQLite 连接没有显式关闭，应使用上下文管理器。
2. 素材文件在扫描后被外部删除时，只有渲染阶段才失败；制作前应重新校验可读性。
3. 快速 fingerprint 只读取首尾各 1MiB，不能作为强完整性哈希；应区分“快速去重指纹”和“发布完整哈希”。
4. 扫描的 OSError 只累计数字，不保存文件路径和原因，用户无法修复权限/坏盘问题。
5. 数据库迁移靠运行时 `ALTER TABLE`，没有 schema 版本、备份和回滚。
6. catalog 使用 WAL，但 job/feedback 数据库未统一并发策略；桌面与 API 同时使用时需压力测试锁竞争。
7. 桌面和 API 分别使用 `desktop_jobs.db`、`production_jobs.db`，任务历史被人为分裂。
8. 桌面扫描一次串行分析最多 10000 条，没有暂停、取消、剩余时间和分批恢复控制。
9. UI 默认素材路径指向不存在的 `runtime_data\test_materials`，干净版首次打开体验错误。
10. UI 没有素材源列表、在线/离线状态、分类修正、分析失败详情和单条重跑入口。
11. 用户配置没有界面，背景音乐路径虽然存在于请求类，但桌面和 API 都没有暴露。
12. TTS 模型每个制作任务重新加载，连续任务浪费时间；应由有界生命周期服务复用。
13. TTS 自动选择“最大 ONNX”，模型目录出现多个 ONNX 时可能选错；应使用模型清单指定文件。
14. 领域词纠正只含三个“岛台”误词，且 Whisper 路线没有同一纠正层；应统一后处理并可配置。
15. 文件名分类在置信度 0.4 时优先于视觉，某些泛化文件名会长期覆盖真实画面分类。
16. 质量中心没有检查 A/V 同步、字幕文字正确性、响度标准、削波、重复镜头、相关性和镜头节奏。
17. 黑屏 10%、冻结 70%、静音 80% 的门槛偏宽，适合防灾难性故障，不等于合格成片标准。
18. 字幕像素验证只看第一条字幕中点；应抽样首中尾多条并结合 OCR/模板区域。
19. 质量失败后项目目录保留，但没有 `FAILED` 状态文件和可视化修复建议。
20. API 工作线程池没有显式 shutdown 生命周期处理；关闭服务时运行任务状态依赖下次恢复。
21. API 只限制绑定本机，没有访问令牌；同一电脑上的其他程序仍可提交任务和写反馈。
22. API/桌面捕获异常后大多只保存一行字符串，没有完整堆栈日志，疑难问题难以定位。
23. API 启动器隐藏进程且不做健康回读，端口占用时用户可能只看到“没反应”。
24. 可以重复启动多个桌面/API 实例，没有单实例锁和明确的进程管理。
25. `pyproject.toml` 没有依赖、入口点、构建后端或锁文件，不能复现当前环境。
26. 交付物不是普通 Windows 安装程序：没有安装/卸载、快捷方式、版本升级、签名和崩溃恢复界面。
27. 没有 SBOM、第三方许可证汇总、模型许可证/来源/哈希清单，商业交付风险未解决。
28. 发布包没有总体文件清单和哈希，复制损坏只能靠少量文件存在检查发现。
29. 发布候选版仍包含 stress/validation/创建发布包等开发脚本，不属于最终用户包。
30. 源码和测试树存在大量 `__pycache__/*.pyc`，属于可清理构建垃圾。
31. `models\Whisper-small` 是空目录，应删除或改成明确的“可选扩展未安装”状态文件。
32. 当前 runtime_data 约 3.37GiB，混有测试素材、缓存、覆盖率审计和历史项目，需要按清单分层，不应跟源码目录长期混放。

## 五、现有测试没有证明的事情

- 没有证明 Qwen 能在任何 NVIDIA 电脑运行。
- 没有证明 1080×1920 最终成片链路存在；当前实际上不存在。
- 没有证明长文案不会截断。
- 没有证明所有配置项有效。
- 没有证明照片/音频素材能处理。
- 没有证明剪映所有目标版本能打开草稿。
- 没有证明模型文件未损坏。
- 没有证明输出画面与卖点真正相关，只证明规则能找到字符命中。
- 没有证明质量中心能发现语义错片、字幕错字和审美问题。
- 没有证明换到 GPU 台式机后仍完全不写 C 盘。

## 六、建议解决顺序

### 第一批：纠正会误导用户或损坏结果的问题

1. 建立分析管线版本与 stale 重跑。
2. 收紧分析成功合同。
3. 关闭正式测试素材默认值。
4. 修复高清 final 渲染和长配音截断。
5. 修复扫描上限和语音旧缓存。
6. 删除/接通无效配置。

### 第二批：建立真正跨电脑运行方案

1. CPU 核心包与 NVIDIA GPU 扩展包分离。
2. 在目标台式机做 Qwen 真推理测试。
3. 从锁定依赖重建单一、无重复的便携 Python。
4. 增加模型/文件 SHA-256 清单与三级诊断。

### 第三批：提升剪辑正确性与用户体验

1. 强化匹配、内容去重和 YOLO 的真实用途。
2. 补齐草稿音频时间线和质量检查。
3. 增加素材库管理、失败详情、取消/暂停和分类修正界面。
4. 建立六类真实素材标注集，用错选率而不是主观口号评估升级。

### 第四批：形成可交付 Windows 产品

1. 统一任务数据库、日志和生命周期。
2. 构建安装/卸载/升级/快捷方式。
3. 增加签名、SBOM、许可证和发布哈希。
4. 精简开发脚本、测试缓存和无效依赖。

## 七、审计结论

v13 的核心链路不是空壳：真实视频探测、抽帧、部分模型推理、离线配音、FFmpeg 渲染、剪映 JSON、任务持久化和质量回读都存在。但当前仍不能称为“全部完善的正式软件”。最需要警惕的不是代码行数太多，而是几处状态与事实不一致：CPU Torch 却承诺 GPU 自动启用、旧部分分析却标成功、预览分辨率却叫最终成片、配置存在却不生效、测试很多却没有覆盖生产主链。

下一阶段应按照本报告顺序逐项修复，并为每个问题增加能失败、能复现、能回归的测试。未经修复前，不应删除旧版或原始测试证据。
