## 4. 存在问题（审计发现）

### 4.1 严重（影响并行化正确性）

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| A1 | **P2 任务领取非原子（check-then-act）**：`should_process()`→`get_state()`→`mark_processing()` 分三步，各开连接，`mark_processing` 是无条件 UPDATE，无 `BEGIN IMMEDIATE`，无 `WHERE status<>'PROCESSING'` 守卫 | `p2_worker.py L89-98` + `processing_state.py L296-327` | **多 Worker 会重复领取同一 asset+stage**，ASR/OCR 重复跑、结果互相覆盖 |
| A2 | **`_transition` 无事务包裹**：读-改-写（SELECT 旧状态 → UPDATE）不加锁，丢失更新 | `processing_state.py L260-307` | 并发状态转移竞争 |
| A3 | **`recover_interrupted_jobs` 每个 worker 进程启动都执行**：把库中所有 `running` 重置为 retry，后启动 worker 会回收先启动 worker 正在处理的任务 | `pool.py L16` + `worker.py L62`（P1 遗留） | 多进程时同任务双跑（P2.5 必须避免此模式） |

### 4.2 中（可扩展性/资源）

| # | 问题 | 位置 |
|---|---|---|
| B1 | ASR 固定 `device="cpu"`，GPU（RTX 3050）闲置 | `asr/engine.py L29-32` |
| B2 | 单进程串行：12 核只用 ~4.4 核，无进程级并行 | `p2_worker.py L228-247` |
| B3 | `--p2-run` 单批退出，无守护/续跑循环 | `main.py L200-208` |
| B4 | 无 Worker 身份标识、无任务级日志（谁在何时处理哪个 asset） | 全局 |
| B5 | 无任务优先级/失败重试上限的调度语义（attempts 有但未用于重试策略） | `p2_worker.py` |
| B6 | 无 `analysis_tasks` 统一任务表；状态散落在 `asset_processing_state`（阶段粒度）与 `analysis_jobs`（P1 遗留） | 全局 |

### 4.3 风险提示

- 直接修改 `p2_worker.py` 会被运行中进程的新一轮 `--p2-run` 调用读到 → **必须旁路：新增模块，不改旧文件语义**
- 数据库已被 6 个模块各自写 `user_version` → 迁移需用独立版本表，不能依赖 user_version
- `assets`/`media_files` 无 `UNIQUE(media_id)` 等约束（并发插入去重风险，P2.5 领取层需自守）

## 5. 改造方案（概要，详见 P2.5_ARCHITECTURE_DESIGN.md）

```
新组件（全部新增，旁路）：
  analysis/scheduler.py      # TaskScheduler：analysis_tasks 管理
  analysis/worker_pool.py    # WorkerPool：N 进程并行
  analysis/worker_p25.py     # P2.5 阶段 worker（scene/keyframe/asr/ocr 复用现有引擎）
  library/task_store.py      # analysis_tasks 表 + 原子领取（BEGIN IMMEDIATE）
  cli: --p2.5-run [--workers N] [--limit M]
```

**核心设计原则**：
1. **旁路**：旧 `--p2-run` 与 `p2_worker.py` 保持原样，运行中进程不受影响
2. **新任务表**：`analysis_tasks`（task_id/asset_id/task_type/status/worker_id/priority/retry_count/时间戳），与旧状态表**双向映射但互不破坏**
3. **原子领取**：`BEGIN IMMEDIATE` + `UPDATE ... WHERE status='pending'` + rowcount 校验（参照 `catalog.claim_job` L506-528 已验证的正确模式）
4. **幂等保护**：任务进入前检查 `asset_processing_state` 对应阶段是否 DONE/SKIPPED，是则跳过；写结果前再次断言
5. **版本表**：新增 `schema_version(name, version)` 表，废除 user_version 依赖
6. **Worker 默认 3**：视觉(scene+keyframe) / ASR / OCR，每进程独立，互不抢任务

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 新 Worker 与旧 PID 19152 同时跑，抢同一批素材 | 升级期间**不启动** P2.5 新 Worker；旧任务跑完后才切换（Step7）。若需并存，领取层以 `asset_processing_state.status='PROCESSING'` 为互斥信号 |
| 数据库被并发写坏 | WAL 已启用；新代码全部走 `BEGIN IMMEDIATE`/单连接事务；busy_timeout=30 |
| 迁移破坏现有数据 | 迁移仅 `CREATE TABLE IF NOT EXISTS` + 新表；**不改旧表结构**；迁移前 sqlite backup |
| 运行中进程读到新文件 | Python 模块已加载进内存；且旧入口文件语义不变（新增文件+新增 argparse 参数） |
| GPU 资源竞争 | 默认全部 CPU 并行；GPU 加速作为后续可选项（预留 device 参数） |

---

## 7. 结论

当前系统作为**单 Worker 串行分析**是正确的、可工作的，但无法支撑 3TB 素材规模。并行化改造**技术上可行**，且系统已具备正确的基础：`catalog.claim_job` 已示范原子领取模式、`asset_processing_state` 已有完善的阶段状态机、WAL 已启用、结果表全部幂等可重入。主要工作量在**新增调度层 + 原子领取 + Worker Pool**，不触碰运行中代码。
